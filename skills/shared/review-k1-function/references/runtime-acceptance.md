# K1 运行验收与自动补验

适用：用户请求运行验收、Unity 实测、复验或继续补验。只做静态预检时不进入本阶段。

## 1. 接续依据与权限

接收静态阶段 PrecheckResult JSON、冻结 manifest、当前开发文档版本、用例及已有用户决定。原文有新变化时，只重新对齐受影响规则；旧决定保留出处和当前适用性，不把历史确认重新展示为全部未决。反馈表复验则保存本次被选中行的原文、稳定 ID 和版本，生成同形的 `metadata` 与 `testcases` 基线 JSON。

先执行 [功能经验读取](feature-experience.md)，从 [索引](../features/index.md) 找到本功能档案及脚本说明，核对本轮版本、入口、配置和授权；已有本轮读取笔记且条件未变时直接接续。原始证据和 plan/state 仍按本工作流保存，经验档案不替代验收台账。

- 运行范围已经授权的直接继续。事实先查；不再次询问可查询的账号状态、GM 语法、部署参数或已批准的操作。
- 只有单号/分支、没有运行请求时，仍按静态入口处理。运行请求不自动授权占用任意服务器、清档、真实付费或改正式配置。用户给定的完整测试范围在后续补验中持续有效。
- 当前任务是测试时，不顺手修业务代码。测试辅助脚本、探针和隔离夹具写在 用户工作区；不要保存场景、关闭 Popup 根节点或回滚用户资源改动。弹窗使用自身 Close / PopupManager 生命周期。
- 静态阻断可以在已获授权的运行范围内定向复现，但不能因实机主流程成功而抹去独立需求缺口。

### 1.1 反馈原图是复验基线的一部分

逐项读取本轮反馈的正文、问题截图、预期/参考图及相关附件；多张图全部查看实际画面，识别标注、错误码、页面和触发条件。仅取得文件名、图片 URL、资源 ID、OCR 或单元格文字，不算已查看图片。

- 表格文字接口返回图片列为空、浮动图片列表为空，都不能证明没有图片。继续用当前可用且获准的图片读取、原表查看或含图片导出路径核实；不要因工具名称或文档声明支持，就宣称图片已读到。
- 为每项保留原文档链接、工作表/稳定反馈 ID/单元格、文档版本、原图定位或证据路径、实际看见的问题特征、与本次实测的对应关系。原图状态明确记为 `已查看 / 已核实无图 / 未取得 / 无法辨认`，后两种填写具体原因、已尝试动作及补证条件。记录随本轮证据和报告交付，不只留在对话中。
- 原图未取得或无法辨认时，不得认定“原截图问题已复现/已修复”，也不得关闭依赖该图的验收项。正文能独立确定的断言继续测试；缺口按真实原因记 pending、blocked 或 missed，未尝试读取属于执行遗漏，不能伪装为环境阻塞。
- 先比对原图与本次场景、现象和报错，再决定是否为同一反馈。尚未建立对应关系的新异常单独记录；把“在哪种场景观察到”与“根因已定位”分开，不能仅因双钩、重连等条件同时出现就认定因果。

## 2. 开测前核验整轮条件

建立运行清单并保存原始证据：

| 项目 | 必须核验的事实 |
|---|---|
| 身份 | Unity 实例、实际 LPlayer 的玩家/服务器/联盟/权限；Inspector 快捷登录字段只代表下一次登录设置 |
| 版本 | 客户端 SHA 与工作区状态、各节点实际镜像/服务端 SHA、配置版本或哈希；部署未知与本地源码参考分开 |
| 时间 | 现实时间及时区、逐服游戏时钟、活动实例 ID/起止时间；明确时间是否只能前进 |
| 配置层次 | 正式 XLSX、发布产物、运行时加载值、平台/网关配置分别记录，不用本地表替代部署证明 |
| 测试条件 | 角色、资源、权限、任务状态、目标容量、跨服依赖、可操作队列、能独立结束的活动、故障模拟能力 |
| 写入边界 | 授权服务器/账号、GM/部署/重启/导入/清档/改时间各自范围及已接受的留存影响 |

用整个用例集合检查条件，不能只确认第一条能跑。缺环境时执行 [jenkins-test-environment.md](jenkins-test-environment.md) 的解析和部署流程。用户已授权复制线上服时，使用 `jenkins_environment_workflow.py` 持续推进备份 → 钉钉 DownKey → 本人同 SID 游戏/战场测试服 → 运行校验，并将 ready 的 `environment-evidence.json` 引用到本台账。战场服未指定列表全量恢复，指定列表按列表保留；不为已确认默认规则重问。部署新服本身不保证活动时间、平台定向、账号和快照已就绪，必须回读。Jira 单号与分支不是可用测试 SID 或可导入数据的授权凭据。

准备 GM 能力表：指令来源、权限、参数单位、作用范围、副作用、恢复限制、前后状态证据。特别检查“恢复进度”是否发奖，“拒绝”是否退盟，“查询”是否推送，以及广播是否包含完整字段。不可凭 GM 名称或 exec succ 判断业务成功。

## 3. 冻结可执行断言计划

复制 `assets/runtime-plan.json` 到 `.tmp/<run-id>/plan.json`，填入实际基线路径及文件 SHA256。按用例拆独立断言，每条写明确的期望、操作、依赖、最晚可执行阶段 `phase`、所需证据类型。保留原用例 ID 和 requirementIds；不把一个断言的成功推广到其他分支，也不增加断言数来改变用例分母。

- `baselineFile` 指向保存的基线 JSON，至少包含 `metadata.documentVersion`、同值 `testcaseDocumentVersion` 和非空 `testcases`（每条含 id、requirementIds、expected）。优先使用静态阶段原始 PrecheckResult。
- `requiredEvidence` 只能选 `ui / protocol / server / runtime / platform / isolated / static / gm`。按原需求确定，正常业务验收不以 gm/isolated/static 代替 runtime/protocol/server；界面和原生 SDK 还需相应 UI/平台证据。
- `phase` 为 0 起整数，同阶段先可重复/负向，再资源消耗与不可逆操作。先核验“新建、取消、边界、失败恢复”等分支，再跨截止时间。并行跨服只并行独立只读采集，共享账号/联盟/Unity 的写操作串行。
- `dependsOn` 是必须通过的前置断言 ID。可行的另一测试前置优先构造，不应因一个失败阻塞整个功能。
- 初始化后计划及基线有哈希绑定，不能删除断言或降低证据要求来结案。需求确实变化时新建修订计划/台账，保留旧版和逐项继承、废止的用户决定；补测使用新环境时同样明确证据批次，不能静默换版本。

在技能目录执行（示例路径需换为本轮实际路径）：

```powershell
python <skillRoot>/scripts/runtime_acceptance.py init --plan <workspaceRoot>/.tmp/<run-id>/plan.json --state <workspaceRoot>/.tmp/<run-id>/state.json
python <skillRoot>/scripts/runtime_acceptance.py next --plan <workspaceRoot>/.tmp/<run-id>/plan.json --state <workspaceRoot>/.tmp/<run-id>/state.json
```

初始化输出待办，不执行游戏动作。**调用此技能的 Agent 必须执行队列，然后更新 state，再次 next；不是把队列交给用户就结束。** 队列按阶段排序，未来阶段的动作先准备环境；不能因列入队列就越过时间检查。

## 4. 执行与证据

每次动作记录前置身份与状态 → 实际入口/请求 → Ack → 适用的最终 Ntf/权威状态 → 界面及资产结果。异步 Ack=0 只代表初步受理；迁服、重连、领奖等还需正常业务落地、重登或持久化核验。直接调用 UI 回调仅证明事件层，不能证明触屏命中区域；截图必须可见目标页面，无其他弹窗遮挡，动画用连续帧。

GM 构造前置、故障注入、隔离生产逻辑测试分别标注。强迁、强制结算不计作正常迁移或自然定时器通过；配置内存 A/B 不计作完整配置发布通过；已存在的 OutOfTime 不等于实测跨期转换。异常返回也检查正确错误码及无意外扣费/发奖。

证据文件为运行目录内路径或绝对本地路径，不能为空。`evidence` 条目格式：`{"kind":"server","path":"evidence/step-01.json"}`。执行状态保存在 `state.results[断言ID]`：

| status | 字段和处理 |
|---|---|
| pending | 未执行；nextAction 可覆盖计划 action，持续排队 |
| partial | observation + evidence + nextAction；中间状态，必须继续 |
| passed | observation + evidence，覆盖全部 requiredEvidence |
| failed | observation + 至少一种 requiredEvidence 范围内的实际失败证据；仅静态推断不能关闭运行断言。归因可另记 implementation/configuration/environment/design，其他独立断言继续 |
| blocked | blocker.kind、reason、attempts、nextAction；每个 attempt 有 action/outcome。环境类另填 options.gm 与 options.jenkins |
| excluded | reason + userDecision，必须能追溯用户明确排除，不把超时/沉默当排除 |
| missed | reason + responsibility + nextAction；如因提前推进错过窗口，直记执行遗漏 |

`blocker.options` 值为 available / exhausted / unavailable / out_of_scope。任一 available 仍进入补验队列；环境阻塞不评估 GM 和 Jenkins 就不能结案。新建依赖阻塞需 `kind=dependency`、`assertionId` 引用本断言 dependsOn 中已 failed/blocked 的项；依赖开始重试时进入 waiting，依赖转为 passed 后脚本自动将原阻塞项重新排入队列。记录仅反映实际尝试，不为满足字段编造失败。

例：
```json
{"status":"blocked","blocker":{"kind":"environment","reason":"现服无法独立结束该活动","attempts":[{"action":"查询时间 GM 作用域","outcome":"作用整个共享服"}],"options":{"gm":"out_of_scope","jenkins":"available"},"nextAction":"在已授权独立测试服部署对应代码和配置，完成真实过期重试"}}
```

此例必须继续部署补验，不是最终阻塞。

### 4.1 新增反馈的截图与在线附件

每条新增问题反馈采集并附上能体现实际表现的本次截图，关联反馈 ID、测试步骤、时间、环境/版本和日志证据。动态或短暂异常使用连续帧或录像；不为补图修改画面、复用无关旧图，原反馈图与本次实测图分别标识。纯协议/后台问题保留实际返回及权威状态，界面截图只证明其可见内容。

- 在用户已授权的反馈文档写入范围内，执行“上传本次图片 → 插入对应反馈项 → 回读该行并打开附件/图片核对”。逐项确认图片属于该反馈、内容正确且文档读者可访问，再记录 `附件已验证`。
- 本地文件路径、图片文件名、上传成功回执或仅返回资源 ID，都不能代替在线附图验证。未完成任一步时明确记录 `截图待上传 / 附件待验证`、本地证据位置、失败环节和补齐条件；可先保存已验证的文字和日志，但不能宣称反馈已附图完整。无法抓取有意义的画面时说明原因和替代证据，不编造截图。
- 上传/插图能力以当前工具实际可用的命令和回读结果为准；没有验证本地图片上传、插入、打开的完整流程前，只能说“接口声明支持，流程尚未验证”。尝试失败后继续其他独立项，保留确实存在的附件缺口。
- 更新表格前后核对原截图、状态下拉的数据验证、选项/颜色和其他非目标内容，使用最小范围写入，不能以纯文本批量覆盖替代保留原单元格结构。

### 4.2 反馈表字段整理与格式保留

适用于反馈表结果同步、补图和精简整理。以实际字段名、稳定反馈 ID 和当前行定位为准，不硬编码某次表格的列字母或行号。

| 字段 | 写入规则 |
|---|---|
| 问题截图 | 本次截图统一追加到对应反馈行的原“问题截图”单元格；一个单元格可包含多张图，保留原图及已有顺序。不要按复验轮次再增加截图列或另建重复问题行。原图、历史实测图、本次实测图需要区分时，在验收详情中简短说明图片顺序及用途。 |
| 验收 | 只保留一个验收状态字段，复用原有下拉选项；不新增“本轮验收”“复验结果”等并列状态列，不把复现步骤或解释塞进状态值。原有开发处理“状态”属于另一用途，不能因精简验收字段而删除或覆盖。 |
| 验收详情 | 合并问题/缺口编号、本轮运行观察及补验条件、原反馈截图复核等补充信息，只留会影响理解或后续行动的内容：复现步骤与实际表现、结论更正或适用边界、尚缺条件和补验动作、必要的图片对应关系。能由原问题、截图或验收状态直接表达的内容不重复，正常通过且无补充说明的行留空。 |

写入和迁移时执行以下核对：

1. **先保存基线。** 保存原表文字、字段/反馈 ID 对应关系、含图副本或图片清单，以及状态下拉的完整数据验证配置（适用范围、选项与顺序、颜色、单/多选及接口可返回的其他约束）。不要把数据验证当作普通单元格文字或显示颜色。
2. **确认追加语义。** 不假定“写图”就是“追加”；替换型接口不得直接写入已有图片的单元格。使用已验证能保留多图的操作，等新增图片保存完成再切换行或刷新；结果不明时先回读，避免重复上传。若现有工具只支持替换，保留原图并尝试获准的多图编辑路径，不能为完成补图覆盖原证据。
3. **保持验证和非目标内容。** 用保留单元格结构的方式更新状态值，不使用会覆盖原验证的整列纯文本粘贴、清空或重建操作。必须迁移列时，连同原有数据验证和格式迁移；新增反馈行也沿用相同规则，随后核对其覆盖范围。意外丢失就按写前基线恢复并再次验证，不用自行猜测的下拉选项替代。
4. **先合并，后精简。** 在已授权的整理范围内，先写入并回读验收详情、完成图片追加，再移除重复列；旧明细页按用户要求收起或归档，保留独有证据。只改字段布局不改变验收结论，原问题与实测的对应关系未闭环时仍保留其结论边界。
5. **最终回读。** 核对每张原图与新增图均挂在正确反馈行、可打开且未丢失或重复；适用时用含图导出的图片位置及哈希比对。另行核对验收状态值、下拉规则、选项/颜色和适用范围，以及其他非目标字段。仅文字一致或写入成功不足以认定整理完成；详细审计记录留在本轮证据中，不重新展开为主表的重复列。

## 5. 自动补验循环与时间检查

每次完成一个场景、条件变化或环境恢复后：

1. 执行 `next`，逐项处理 `nextActions`。优先当前阶段即将过期的断言；现有条件 → GM/故障模拟 → Jenkins 独立环境。已有授权内持续执行，不等待用户说“继续”。
2. 核验真实结果后更新状态和证据。不能只把 partial 改成 passed，不记录新证据。
3. 检查 `waiting`：先解决依赖；确实无法继续才记录有依据的 dependency blocker。一个主流程失败并不清空后续独立任务。
4. 反复执行直到没有可继续动作。权限/事实信息确实缺失才问最小问题，其他独立验证继续。工具失败先检查实例、编译/重载、连接和身份，不无进展重复，也不默认重启丢弃未保存状态。
5. 场景/阶段结束、版本变化及交接或中断前，按 [经验更新规则](feature-experience.md) 保存本轮增量并合入功能档案；必要的可复用运行模板一并归档。失败、阻塞或部分验证也记录已掌握的事实和下次动作；恢复时先处理尚未回写的笔记。

推进时间之前：
```powershell
python <skillRoot>/scripts/runtime_acceptance.py check-advance --plan <plan.json> --state <state.json> --target-phase 1
```
返回 allowed 才按确认的 GM 语法读取当前逐服时钟，计算正增量并操作。工具不替你改时间；推进后再次回读各服和客户端时钟，保存证据，再更新 `currentPhase`。尚未闭环且会过期的断言会拒绝推进，包括真实阻塞；优先准备可重测的新环境，不擅自牺牲覆盖。确实决定放弃的分支需用户已有明确决定才可 excluded。当前会话规定不能回拨时，禁止使用其他 skill 示例中的 timeset/timereset 或旧快照规避。

环境改动/重启前保存易丢失日志。重启后的暂时缺广播、缓存未就绪与真实数据丢失分开验证。运行版本变化时记录新证据批次，核对语义差异后才复用旧结果。

## 6. 收尾与最终发布

`state.environmentEvidence` 保存实际身份/版本/时间/实例证据。`state.cleanup` 至少包含 verified=true、非空 evidence、retainedChanges（账号现属服/联盟、资源变化、游戏时间、剩余申请、无法恢复状态等）。注销采样器和网络拦截，确认无暂存响应；仅恢复本次可恢复的人工前置，保留自然恢复/正常业务变化，不因“恢复”再发奖或覆盖其他人修改。

```powershell
python <skillRoot>/scripts/runtime_acceptance.py publish --plan <plan.json> --state <state.json> --output <workspaceRoot>/reports/<unique-runtime-run-id>
```

发布入口强制检查基线/计划未漂移、用例与断言未丢失、证据范围及文件、可继续项为零、清理和环境记录。可继续项存在时失败且不生成报告目录。真实阻塞、已明确排除和执行遗漏可结束本轮，但不能给完整验收通过；只有全部断言 passed 且收尾完成才能 fullyAccepted=true。

结果输出 `summary.html` 与 `runtime-result.json`，包含逐断言观察、证据和剩余动作。报告区分用例数量、唯一缺陷数量和验证方式；同一个缺陷影响多条用例不能重复计作多个缺陷。用户修正设计/归因时保留原证据和决定，不冒充又做了一次实测。

校验器只能检查记录一致性，不能证明证据真实或要求解释正确。最终还需按文档逐项检查是否漏拆分支、是否错用证据。对话说明实际覆盖、主要问题、不可恢复影响及报告入口；有范围缺口就明确未完整通过。

交付前回读功能档案和索引，说明本轮新增/修订/失效经验及脚本、或无新增；写入失败则提供本轮 `experience-notes.md` 中的待回写内容。CLI 发布通过不证明经验已更新，经验归档完成也不改变业务验收结果。

反馈表任务另需逐项检查原图查看记录、原问题与实测的对应依据及新增反馈的在线附件验证，并按 §4.2 核对多图归位、唯一验收状态字段、精简后的验收详情及原有下拉验证；本地报告生成成功不代表原图已核对或线上附图已完成。原图或附图缺口必须在最终交付中单列。

## AI 工作流接入

统一入口和合同见 [AI 验收工作流](ai-acceptance-workflow.md)。新批次依旧经过本文的覆盖、证据和清理门槛；影响分析 reuse_candidate 不是已通过，沿用需显式确认和等价证据。录制无唯一请求关联、未注销探针、未回读资产、未取得自然到期条件时保留具体缺口。重连后的新 session 不接受旧快照清理。
