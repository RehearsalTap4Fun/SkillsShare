# 需求对齐前置工作流

## 顺序与完成依据

本工作流必须先于用例生成/校准和静态预审完成：冻结三端版本 → 比对文档与提交/最终状态 → 展示增删改 → 用户确认 → 维护原文档并回读 → 交接。不是启动预审后的暂停点。对齐与预审均不限时。

三端仓库保持只读；Git 与正式 XLSX 取证遵守 `k1-project.md`。只有用户确认的需求调整允许更新指定的原策划文档。实际文档必须可读、可维护；未知项不得伪装成完整准确的事实。

## 1. 固定输入与覆盖范围

- 读取原文档全文（包括分页、子块、表格及与需求相关的附件），记录唯一来源、版本/更新时间及内容指纹；按文档顺序给每项需求稳定 ID 和定位。
- 在本次 `.tmp/<run-id>` 保存必要的原文快照和三端 manifest。完整在线正文不得写入通用分析缓存或最终报告。
- 普通分支在工作流开始时实时从 origin 冻结 base/target SHA。默认 baseBranch=dev、三端同名 target；覆盖参数沿用原有约定。
- 用 collector 的 `baseSha..targetSha` commits 了解意图、`baseSha...targetSha`（merge-base 到 target）累计 diff 定位变化，读取 target 最终代码与正式 XLSX 核实当前行为。撤销、覆盖的中间提交不单独作为仍有效的变更。
- 对齐、用户确认、文档维护、用例和预审使用同一 manifest。等待不刷新 ref，不受 24 小时分析缓存 TTL 影响；对象不可读时补取同一 SHA，不能替换成最新分支。用户要纳入新提交时开始新的对齐记录。
- 双向核查：逐条覆盖文档需求，同时逐项检查分支相关变更是否引入文档未提及的规则。记录无关提交/文件的排除理由；纯重构、格式和生成文件变化不自动列为需求变化。
- 某端未取得 SHA 时，不填假 SHA、不用本地分支替代。repositories 仅包含成功冻结的端；把 preparer 原始 errors 中的 `{role, code}` 原样放入 metadata 和 alignment 的 `unavailableRepositories`。成功端与失败端合起来必须恰好覆盖三端，不能重叠。保留原始 manifest；相关需求/差异明确无法确认，继续可核查范围并保留问题，不能宣称三端均已核实。
- 从 diff 向业务入口、权限、协议、服务端状态、正式配置、展示反馈追踪必要依赖，直到需求条件可判定或有明确外部障碍；无固定一跳/一轮上限，禁止无目标全仓扫描。

## 2. 面向用户的增删改清单

使用 `assets/requirement-alignment.md`。每条 `ALN-xxx` 必须有：

| 字段 | 内容 |
|---|---|
| 候选变化 | 新增 / 删除 / 修改 / 待判定；这是候选，不代表已批准 |
| 文档依据 | 原文原句、章节/块定位；新增写「原文未定义」 |
| 实现行为 | 三端最终行为、跨端是否一致；分开写已核实事实与推测 |
| 变更依据 | 对应端、提交 SHA/意图、target SHA、代码完整片段或正式表/行/字段 |
| 建议修订 | 将写入原文的完整替换文本、插入位置或准确删除范围 |
| 影响 | 受影响需求 ID、已有用例、边界与异常路径 |
| 用户决定 | 需求已调整 / 实现有问题 / 证据不足 |

“文档有而代码未找到”不能直接认定需求删除；“未出现在 diff”、无本端提交、两端代码一致或提交说明写“按策划调整”，也不能代替最终证据和用户确认。配置无法物化时仍为证据不足，不提升生成 JSON 为权威。

所有需求必须有覆盖记录（相符、候选差异或无法确认）；`comparisonSummary` 概述文档范围、三端变更范围、排除项和剩余证据缺口。无差异也必须完成实际双向检查并记录，不得用空数组跳过分析。

## 3. 用户确认

向用户展示完整清单和建议文案，按 ID 支持一次批量回复，例如「ALN-01、03 需求已调整；02 实现有问题；04 证据不足」。保存每条的实际回复依据 `confirmation`，包含消息定位/时间或可追溯原话；不能由 Agent 编造确认。

- **需求已调整**：只写入用户批准的具体增删改文本，用户修正建议时以修正文案为准。
- **实现有问题**：保留原文；记录问题和关联需求，交给后续预审核查，不在此步骤修代码。
- **证据不足**：保留原文；写清缺口、补证或运行验收动作，交接到预审，不推断为删除或修改。
- 待判定候选可以由用户决定为实现有问题/证据不足；要更新文档则必须先明确为新增、删除或修改及准确文案。
- 部分回复只确认覆盖到的 ID。其余仍待确认，前置工作流尚未完成。不得把沉默、模糊“看情况”或工具失败当作同意。
- 无差异时记录空清单与回读结果，顺序进入后续工作流，无需让用户确认空清单。

## 4. 最小维护原文与回读

1. 写入前重新读取原文并比对前次版本/指纹。若发生他人编辑，保留对方内容；重新比对受影响差异及建议补丁，重新取得受影响条目的确认。不得拿旧全文覆盖新文档。
2. 钉钉源优先使用连接的文档工具读取块并修改指定块，保留其他内容、表格、图片和附件；本地 Markdown/TXT 做精确替换；DOCX 按 documents skill 最小修改。PDF、无写权限或不可编辑源不能伪报更新：交付待写补丁，说明需要可编辑源或权限，前置阶段保持未完成。
3. 写入前记录可恢复的版本标识或本次原文快照。只更新「需求已调整」的章节；原文档处于正式 K1 仓库内时仍不得写仓库，需明确可维护的文档来源。
4. 追加简短变更记录：日期、ALN ID、变更前后语义、用户决定/确认依据、相关三端提交和 target SHA。被删除规则也保留历史记录；不只追加附录而留下冲突正文。
5. 写入后重新读取原文：核对批准补丁已生效、未批准内容没有被改动、原有结构/附件保留、变更记录存在，保存 `afterVersion` 和实际内容指纹。仅写入接口返回成功不能设置 `readBackVerified=true`。
6. 部分失败时按 ALN ID 记录已写入与未写入条目。重试前再次回读，跳过已生效的正文和日志，避免重复插入；不自动整体回滚覆盖他人修改。全部批准条目成功且回读通过才置为 completed。

没有批准的文档修改时，`writeStatus=unchanged` 且前后内容版本相同；也要重新确认源文档未漂移。混合清单只对批准项写入，其他项继续保留和交接。

## 5. 机器可校验的交接记录

在本次 `.tmp/<run-id>/handoff.json` 保存以下结构；生成用例前运行校验器：

```json
{
  "metadata": {
    "documentSource": "原文档来源",
    "documentVersion": "回读后的内容指纹或稳定版本",
    "repositories": ["复制报告所需的三端 role/source/remote/baseRef/targetRef/base/target 对象"]
  },
  "alignment": {
    "schemaVersion": 1,
    "status": "completed",
    "comparisonSummary": "已覆盖的需求、三端提交、排除项及证据缺口",
    "repositories": ["与 metadata 完全相同的三端冻结身份"],
    "document": {
      "source": "原文档来源",
      "beforeVersion": "原内容指纹或稳定版本",
      "afterVersion": "回读后的内容指纹或稳定版本",
      "writeStatus": "updated",
      "readBackVerified": true,
      "changeLogLocator": "变更记录的章节或块定位"
    },
    "changes": [{
      "id": "ALN-01",
      "changeType": "修改",
      "documentLocator": "次数限制",
      "original": "每天 5 次",
      "implementation": "客户端与服务端最终代码限制为每天 8 次，提交证据见清单",
      "proposed": "每天 8 次",
      "evidence": ["与预审 evidence 同形的 target 最终状态证据，代码必须有 snippet"],
      "decision": "需求已调整",
      "confirmation": "实际用户回复定位及确认内容",
      "applied": true,
      "requirementIds": ["REQ-01"],
      "followup": "按 8 次校准边界用例并检查跨端一致性"
    }]
  }
}
```

示例中的 repositories/evidence 字符串是结构说明，必须替换为实际对象，不可直接运行。需求已调整必须 applied=true 且有证据；实现有问题/证据不足必须 applied=false。后两类必须有保留的 requirementIds 与 followup；只有已批准删除的需求可以没有后续 requirementIds。

```powershell
python <skillRoot>/scripts/requirement_alignment.py --input <workspaceRoot>/.tmp/<run-id>/handoff.json
```

校验失败不进入用例工作流。校验成功后将 alignment 原样加入 PrecheckResult，校准完成才记录 `metadata.testcaseDocumentVersion=metadata.documentVersion`。renderer 再核对三端 SHA/refs、文档版本、回写状态、确认记录和需求交接；并核对差异引用的代码定位。校验只证明记录一致性，不能代替真实用户确认与在线文档回读。

存在 unavailableRepositories 时，前置校验命令额外传 `--evidence-manifest <原始manifest.json>`。renderer 同样要求失败记录与该原始 manifest.errors 一致，不允许人为抹去或新增失败端；相关端仍参与语义规则匹配，检查结果必须为无法确认。报告显示失败端与错误码；没有已证实阻断时总体结论为预检信息不足，不能发布为可进入运行验收。

## 6. 交接与恢复

用更新后文档重新建立完整需求矩阵，新增需求补用例，修改需求校准旧期望，删除需求的旧用例退出当前集合并保留变更记录。无条数上限，已有用例不得直接复用旧期望。

每项仍有效的需求至少关联一条用例，包括必须运行才能判断的表现需求。renderer 强制检查非空覆盖和双向引用；版本相同只证明记录一致，不能代替逐条检查用例期望是否符合已确认规则。

实现问题和未知项进入同一批冻结版本的预审，按 requirementIds 逐项补证，结果、解释及验收动作保留其处理结论。证据不足可能在补证后解决，但不可静默丢弃。

恢复同一工作流先核对 manifest、用户确认记录、源文档回读版本和已应用条目；等待或缓存 TTL 不能改变审核对象。原文又有新修改时重新对齐受影响内容、校准用例，不能以旧记录发布新文档的预审结论。
